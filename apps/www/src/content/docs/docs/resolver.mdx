A resolver document is a JSON file that defines how to load and combine your design tokens. It specifies which token files to load, in which order, and how theming variations work.

sugarcube always reads your tokens through a resolver, even when you only have one token file. For one file, the required resolver is short:

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    { "type": "set", "name": "base", "sources": [{ "$ref": "./tokens.json" }] }
  ]
}
```

## Basic structure

A resolver document has two main parts:

1. **Sets** — Groups of token source files
2. **Modifiers** — Theming variations (like light/dark)

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    {
      "type": "set",
      "name": "base",
      "sources": [
        { "$ref": "./colors.json" },
        { "$ref": "./spacing.json" }
      ]
    },
    {
      "type": "modifier",
      "name": "theme",
      "default": "light",
      "contexts": {
        "light": [],
        "dark": [{ "$ref": "./dark.json" }]
      }
    }
  ]
}
```

A resolver file may have comments and trailing commas, since the spec lets tools read it as JSONC. Token files stay plain JSON.

## Auto-discovery

Sugarcube automatically discovers a `*.resolver.json` file in your project, so you typically don't need to configure the resolver path. It skips `node_modules`, build folders and hidden folders such as `.storybook`, so a resolver kept in a hidden folder needs naming.

If there are several resolver files, sugarcube asks you to choose:

```text frame="none"
Several resolver files were found:
  - tokens/other.resolver.json
  - tokens/tokens.resolver.json

Name the one to use as `resolver` in sugarcube.config.ts.
```

Specify which one to use in your config, or with `--resolver` on the command line:

```ts title="sugarcube.config.ts"
import { defineConfig } from "@sugarcube-sh/vite";

export default defineConfig({
  resolver: "src/design-tokens/tokens.resolver.json"
});
```

## Sets

A set groups related token sources together. Use sets to organize your tokens logically:

```json
{
  "type": "set",
  "name": "base",
  "sources": [
    { "$ref": "./palette.json" },
    { "$ref": "./colors.json" },
    { "$ref": "./typography.json" },
    { "$ref": "./spacing.json" }
  ]
}
```

### Source references

Sources use `$ref` to reference external files. Paths are relative to the resolver document:

```json
{ "$ref": "./colors.json" }        // Same directory
{ "$ref": "../shared/tokens.json" } // Parent directory
{ "$ref": "./tokens/base.json" }   // Subdirectory
```

### Multiple sets

You can define multiple sets. Tokens from later sets override earlier ones:

```json
{
  "resolutionOrder": [
    {
      "type": "set",
      "name": "foundation",
      "sources": [{ "$ref": "./foundation.json" }]
    },
    {
      "type": "set",
      "name": "semantic",
      "sources": [{ "$ref": "./semantic.json" }]
    }
  ]
}
```

## Private sets

Sometimes you want tokens to take part in resolution — so other tokens can reference them — without emitting them as CSS variables. A common case is a raw or primitive token set that exists only as scaffolding for your semantic tokens.

Mark a set or an individual source as private with the `sh.sugarcube` extension:

```json title="tokens.resolver.json"
{
  "type": "set",
  "name": "base",
  "sources": [
    {
      "$ref": "./palette.json",
      "$extensions": { "sh.sugarcube": { "emit": false } }
    },
    { "$ref": "./colors.json" }
  ]
}
```

Now `palette.json`'s tokens resolve as normal, but no variables are emitted for them. Any public token that references a private one is inlined to its resolved value:

```css
:root {
  /* color.danger -> {palette.red.600} gets inlined like so */
  --color-danger: #e11d48;
}
```

You can set it per source, as above, or per set, which covers every source in it:

```json
{
  "type": "set",
  "name": "raw",
  "$extensions": { "sh.sugarcube": { "emit": false } },
  "sources": [
    { "$ref": "./palette.json" },
    { "$ref": "./size.json" }
  ]
}
```

### When settings are nested

When a set and a source inside it say different things, the nearest setting wins: the source's own, then the set's. So a private set can still make one of its sources public:

```json
{
  "type": "set",
  "name": "raw",
  "$extensions": { "sh.sugarcube": { "emit": false } },
  "sources": [
    { "$ref": "./palette.json" },
    {
      "$ref": "./spacing.json",
      "$extensions": { "sh.sugarcube": { "emit": true } }
    }
  ]
}
```

`palette.json`'s tokens stay private, and `spacing.json`'s are written. A public token that refers to a private one is inlined, as before:

```css
:root {
  /* space.md -> {size.4}, a private token from palette.json, so inlined */
  --space-md: 16px;
}
```

## Modifiers

Modifiers provide themed variations of your tokens. See [Theming](/docs/theming) for full details.

```json
{
  "type": "modifier",
  "name": "theme",
  "default": "light",
  "contexts": {
    "light": [],
    "dark": [{ "$ref": "./dark.json" }]
  }
}
```

- **`name`** — The modifier name
- **`default`** — Which context is the baseline, used when no input is given. Without `permutations` in your config, sugarcube needs one: a modifier with no default is an error
- **`contexts`** — Map of context names to source arrays

The resolver defines *what* your modifier contexts are. By default, the default context goes to `:root`, and each other context gets a `[data-{modifier}="{context}"]` block. To use other selectors, list `permutations` in your config. See [Theming](/docs/theming) for details.

## Resolution order

The `resolutionOrder` array controls how tokens are processed:

1. Items are processed top to bottom
2. Later tokens override earlier ones with the same path
3. Sets provide base values, modifiers provide overrides

```json
{
  "resolutionOrder": [
    { "type": "set", "name": "base", "sources": [...] },     // First: base tokens
    { "type": "set", "name": "semantic", "sources": [...] }, // Second: semantic layer
    { "type": "modifier", "name": "theme", ... }             // Third: theme overrides
  ]
}
```

## Version

Always include `"version": "2025.10"` at the top of your resolver:

```json
{
  "version": "2025.10",
  "resolutionOrder": [...]
}
```

This identifies the resolver format and ensures compatibility.

## File naming

By convention, resolver files use the `.resolver.json` extension:

```
src/design-tokens/
├── tokens.resolver.json  ← Resolver document
├── colors.json           ← Token file
├── spacing.json          ← Token file
└── dark.json             ← Theme override file
```

<SiteAside type="tip">
  The `.resolver.json` extension makes it clear which file is the entry point for your token system.
</SiteAside>

## Complete example

Here's a complete resolver with base tokens and a light/dark theme:

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    {
      "type": "set",
      "name": "base",
      "sources": [
        { "$ref": "./palette.json" },
        { "$ref": "./colors.json" },
        { "$ref": "./borders.json" },
        { "$ref": "./spacing.json" },
        { "$ref": "./typography.json" }
      ]
    },
    {
      "type": "modifier",
      "name": "theme",
      "default": "light",
      "contexts": {
        "light": [],
        "dark": [{ "$ref": "./dark.json" }]
      }
    }
  ]
}
```
