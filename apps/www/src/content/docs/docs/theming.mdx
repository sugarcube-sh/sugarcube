Sugarcube supports theming through **modifiers** — named variations that override your base token values.

## Basic: zero-config dark mode

Define a modifier with a `default` in your [resolver document](/docs/resolver) and you're done. No config file needed.

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    {
      "type": "set",
      "name": "base",
      "sources": [
        { "$ref": "./colors.json" },
        { "$ref": "./spacing.json" }
      ]
    },
    {
      "type": "modifier",
      "name": "theme",
      "default": "light",
      "contexts": {
        "light": [],
        "dark": [{ "$ref": "./dark.json" }]
      }
    }
  ]
}
```

Sugarcube generates:

```css
:root {
  --color-surface: #ffffff;
  --color-text: #1a1a1a;
}

[data-theme="dark"] {
  --color-surface: #1a1a1a;
  --color-text: #ffffff;
}
```

The default context ("light") goes to `:root`. Non-default contexts get a `[data-{modifier}="{context}"]` selector automatically. Each block declares what its context changes, plus the variables that refer to what it changed, so the theme also works on a nested element (see [Theming nested elements](#theming-nested-elements)).

### Using it in HTML

Set the data attribute to switch themes:

```html
<!-- Light mode (default — no attribute needed) -->
<html>

<!-- Dark mode -->
<html data-theme="dark">
```

You can scope themes to specific elements too:

```html
<div data-theme="dark">
  <!-- only this section uses dark variables -->
</div>
```

### Override files

Override files only need the tokens that change. Everything else inherits from the base set:

```json title="dark.json"
{
  "color": {
    "$type": "color",
    "surface": { "$value": "#1a1a1a" },
    "text": { "$value": "#ffffff" }
  }
}
```

<SiteAside type="tip">
  Keep override files focused. Only include tokens that actually change — this makes it clear what each theme modifies.
</SiteAside>

### More than two contexts

You can define as many contexts as you need:

```json
{
  "type": "modifier",
  "name": "theme",
  "default": "light",
  "contexts": {
    "light": [],
    "dark": [{ "$ref": "./dark.json" }],
    "high-contrast": [{ "$ref": "./high-contrast.json" }]
  }
}
```

Generates:

```css
:root { /* light */ }
[data-theme="dark"] { /* dark overrides */ }
[data-theme="high-contrast"] { /* high-contrast overrides */ }
```

## Custom selectors: the permutations API

When the auto-generated data attribute selectors aren't enough, use `variables.permutations` in your config to control exactly how each context maps to CSS.

### Media queries

Follow the user's OS preference with zero JavaScript:

```ts title="sugarcube.config.ts"
import { defineConfig } from "@sugarcube-sh/cli";

export default defineConfig({
  resolver: "./tokens.resolver.json",
  variables: {
    permutations: [
      { input: { theme: "light" }, selector: ":root" },
      {
        input: { theme: "dark" },
        selector: ":root",
        atRule: "@media (prefers-color-scheme: dark)"
      },
    ]
  }
});
```

Output:

```css
:root {
  --color-surface: #ffffff;
}

@media (prefers-color-scheme: dark) {
  :root {
    --color-surface: #1a1a1a;
  }
}
```

The `atRule` option works with any CSS at-rule — `prefers-color-scheme`, `prefers-contrast`, `pointer`, etc.

<SiteAside type="note">
  When you define `permutations`, nothing is generated for you. List every context you want, the default first. Listed later, the default block overrides the others, and sugarcube warns: `the default isn't listed first`. Leave the light permutation out above, and you get only the dark media query block, so light users get no variables.
</SiteAside>

### Compound selectors

Selectors can be arrays — they get comma-joined in the output:

```ts
{
  input: { theme: "dark" },
  selector: [
    "[data-color-mode=light][data-light-theme*=dark]",
    "[data-color-mode=dark][data-dark-theme*=dark]"
  ]
}
```

Output:

```css
[data-color-mode=light][data-light-theme*=dark],
[data-color-mode=dark][data-dark-theme*=dark] {
  --color-surface: #1a1a1a;
}
```

### Using --input from the CLI

The `--input` flag is equivalent to defining a single permutation. Use it for one-off builds:

```bash frame="none"
sugarcube generate --input theme=dark --selector "[data-theme='dark']"
```

Without `--selector`, output goes to `:root`:

```bash frame="none"
sugarcube generate --input brand=ocean --variables dist/ocean.css --variables-only
```

<SiteAside type="note">
  When `--input` is used alongside a config that defines `permutations`, the config permutations are ignored. The `--input` flag always takes priority.
</SiteAside>

## Advanced: multiple modifiers and brands

### Multiple modifiers

A resolver can have more than one modifier. A common example is **brand** (palette colors) and **theme** (light/dark surfaces). These are separate concerns that don't overlap:

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    {
      "type": "set",
      "name": "base",
      "sources": [{ "$ref": "./base.json" }]
    },
    {
      "type": "modifier",
      "name": "brand",
      "default": "default",
      "contexts": {
        "default": [],
        "ocean": [{ "$ref": "./ocean.json" }],
        "forest": [{ "$ref": "./forest.json" }]
      }
    },
    {
      "type": "modifier",
      "name": "theme",
      "default": "light",
      "contexts": {
        "light": [],
        "dark": [{ "$ref": "./dark.json" }]
      }
    }
  ]
}
```

You don't need a config for this. Each context of each modifier gets its own block, in the resolver's order:

```css
:root { --color-primary: red; --color-surface: white; }
[data-brand="ocean"] { --color-primary: blue; }
[data-brand="forest"] { --color-primary: green; }
[data-theme="dark"] { --color-surface: #1a1a1a; }
```

In HTML, set a data attribute for each active context:

```html
<html data-brand="ocean" data-theme="dark">
  <!-- gets --color-primary: blue from brand, --color-surface: #1a1a1a from theme -->
```

This works because the modifiers are **orthogonal** — they override different tokens, so there's no conflict. The DTCG spec [recommends this approach](https://www.designtokens.org/TR/2025.10/resolver/#orthogonality).

To use other selectors, list a permutation for each context in your config, as in [Custom selectors](#custom-selectors-the-permutations-api), in the resolver's order:

```ts title="sugarcube.config.ts"
import { defineConfig } from "@sugarcube-sh/cli";

export default defineConfig({
  resolver: "./tokens.resolver.json",
  variables: {
    permutations: [
      { input: {}, selector: ":root" },
      { input: { brand: "ocean" }, selector: ".brand-ocean" },
      { input: { brand: "forest" }, selector: ".brand-forest" },
      { input: { theme: "dark" }, selector: ".dark" },
    ]
  }
});
```

### When modifiers aren't orthogonal

The examples above work because brand and theme override different tokens — brand changes `color.primary`, theme changes `color.surface`. But what if Brand Ocean's dark surface needs to be a dark blue, while Brand Forest's dark surface is a dark green? Now both modifiers want to override `color.surface`, and the last one wins — you lose the brand-specific value.

### Keep the blocks in the resolver's order

When two modifiers change the same token, the resolver says which wins: the one later in `resolutionOrder`. In CSS, the block written later wins, so the blocks must come in the same order. Without a config, they do. With `permutations` in your config, list them in the resolver's order: every `brand` block before every `theme` block here.

Listed the other way round, the CSS disagrees with your tokens, and nothing warns you. Say `ocean.json` sets `color.surface` to a light blue, and `dark.json` sets it to `#1a1a1a`. The resolver says `brand: ocean` with `theme: dark` has the dark surface. But with the dark block written first, the CSS has, among the rest:

```css
[data-theme="dark"] { --color-surface: #1a1a1a; }
[data-brand="ocean"] { --color-primary: #0000ff; --color-surface: #e0f0ff; }
```

`<html data-brand="ocean" data-theme="dark">` gets the light blue surface, because the brand block comes later.

### Composed contexts

When a brand needs its own values in dark mode, such as Ocean's dark blue surface, add composed contexts to the theme modifier for each brand-specific combination:

```json title="tokens.resolver.json"
{
  "version": "2025.10",
  "resolutionOrder": [
    {
      "type": "set",
      "name": "base",
      "sources": [{ "$ref": "./base.json" }]
    },
    {
      "type": "modifier",
      "name": "brand",
      "default": "default",
      "contexts": {
        "default": [],
        "ocean": [{ "$ref": "./ocean.json" }],
        "forest": [{ "$ref": "./forest.json" }]
      }
    },
    {
      "type": "modifier",
      "name": "theme",
      "default": "light",
      "contexts": {
        "light": [],
        "dark": [{ "$ref": "./dark.json" }],
        "dark-ocean": [{ "$ref": "./dark.json" }, { "$ref": "./dark-ocean.json" }],
        "dark-forest": [{ "$ref": "./dark.json" }, { "$ref": "./dark-forest.json" }]
      }
    }
  ]
}
```

The brand modifier stays separate — it handles brand colors. The theme modifier gets composed contexts for each brand that needs dark-mode-specific overrides. `dark.json` is shared across all of them, and `dark-ocean.json` only contains the exceptions:

```json title="dark-ocean.json"
{
  "color": {
    "$type": "color",
    "surface": { "$value": "#0c2d3f" }
  }
}
```

Each context gets its own block, such as `[data-theme="dark-ocean"]`. Set the brand and its composed theme together:

```html
<html data-brand="ocean" data-theme="dark-ocean">
```

The number of theme contexts grows with the number of brand × mode combinations, but each override file stays small — only the tokens that actually differ from the generic dark mode.

### Per-brand output files

Instead of one CSS file with all brands, you can generate a separate file per brand. Use the `path` option:

```ts title="sugarcube.config.ts"
variables: {
  permutations: [
    { input: { brand: "ocean" }, selector: ":root", path: "dist/ocean.css" },
    { input: { brand: "forest" }, selector: ":root", path: "dist/forest.css" },
  ]
}
```

Or from the CLI:

```bash frame="none"
sugarcube generate --input brand=ocean --variables dist/ocean.css --variables-only
sugarcube generate --input brand=forest --variables dist/forest.css --variables-only
sugarcube generate --utilities-only
```

### Resolution order

Modifiers in `resolutionOrder` are applied in sequence. Later entries override earlier ones:

```json
{
  "resolutionOrder": [
    { "type": "set", "name": "base", "sources": [...] },
    { "type": "modifier", "name": "brand", ... },
    { "type": "modifier", "name": "theme", ... }
  ]
}
```

If two modifiers override the same token, the one later in the array wins. Structure your resolver accordingly, and keep your CSS blocks in the same order (see [above](#keep-the-blocks-in-the-resolvers-order)).

### Theming nested elements

Usually you set a theme on `<html>` and everything inside inherits it. But sometimes you want to theme just part of a page — a card, a sidebar, an embedded preview — by putting `data-theme` on a nested element instead of the root.

That needs care when your tokens reference each other in a chain. CSS works out a `var()` where the variable is declared, and inherits the result, not the `var()` chain. So if `--background-accent: var(--binding-accent)` is declared only on `:root`, a nested element keeps `:root`'s accent even when its theme repoints `--binding-accent`.

sugarcube handles this for you: each block also declares again every variable that refers to something it changed, all the way down the chain, composite values included, such as a shadow whose color refers to a changed variable:

```css
:root {
  --binding-accent: var(--blue-600);
  --background-accent: var(--binding-accent);
}

[data-theme="brand"] {
  --binding-accent: var(--teal-600);
  --background-accent: var(--binding-accent);
}
```

`--background-accent` is declared again in the brand block, so it works out to teal on any element with `data-theme="brand"`.

<SiteAside type="note">
  This makes each block bigger. If your themes are only ever set on `<html>`, you can turn it off for smaller CSS:

  ```ts title="sugarcube.config.ts"
  export default defineConfig({
    variables: {
      redeclareDependents: false,
    }
  });
  ```

  Then the brand block above declares only `--binding-accent`. It was called `propagateDependents` and was off by default; the old name still works, with a warning, until 1.0.
</SiteAside>
