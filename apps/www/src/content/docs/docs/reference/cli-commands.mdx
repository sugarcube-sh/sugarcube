## `init`

Initialize a new sugarcube project interactively.

### Usage

```bash frame="none"
npx @sugarcube-sh/cli init [options]
```

### Description

The `init` command walks you through setting up sugarcube in your project. It:

- Detects existing design tokens, or prompts you to choose a starter kit
- Optionally adds CUBE CSS files
- Optionally adds components from the registry
- Optionally installs the Vite plugin
- Installs `@sugarcube-sh/cli` as a dev dependency

No config file is created — the project works with auto-discovery and sensible defaults. See [Configuration](/docs/configuration) for customizing settings later.

### Options

<Table>
| Option | Description | Default |
|--------|-------------|---------|
| `--tokens <dir>` | Design tokens directory | Auto-detected based on `src/` |
| `--cube <dir>` | CUBE CSS output directory | Auto-detected based on `src/` |
| `--components <dir>` | Components output directory | Auto-detected based on `src/` |
</Table>

<SiteAside type="note">
    Requires an interactive terminal. For CI or non-interactive use, use the individual commands (`generate`, `cube`, `components`) directly.
</SiteAside>

### Examples

```bash frame="none"
# Interactive initialization with defaults
npx @sugarcube-sh/cli init

# Specify custom directories
npx @sugarcube-sh/cli init --tokens ./tokens --cube ./css
```

## `generate`

Generate CSS variables and utility classes from your design tokens.

### Usage

```bash frame="none"
npx sugarcube generate [options]
```

### Description

The `generate` command reads your design tokens and writes:

- CSS variables from your tokens
- Utility classes, from the utilities in your configuration, for the classes your markup uses and any in a `safelist`

It works with no config at all, finding your resolver for you. You can change the main settings with flags.

<SiteAside type="note">
    This command is not needed if you're using the **Vite plugin**, which generates virtual CSS modules automatically.
</SiteAside>

### Options

<Table>
| Option | Description | Default |
|--------|-------------|---------|
| `--resolver <path>` | Path to your resolver file | Found for you |
| `--variables <path>` | Output path for CSS variables | `src/styles/variables.gen.css` |
| `--utilities <path>` | Output path for utility classes | `src/styles/utilities.gen.css` |
| `--fluid-min <number>` | Min viewport for fluid scaling | `320` |
| `--fluid-max <number>` | Max viewport for fluid scaling | `1200` |
| `--color-fallback <strategy>` | Color fallback: `native` or `polyfill` | `native` |
| `--prefix <string>` | Text put before every CSS variable name | - |
| `--input <modifier=value>` | Select a modifier context for this build (repeatable) | - |
| `--selector <selector>` | CSS selector for `--input` output | `:root` |
| `--variables-only` | Generate only CSS variables, skip utilities | - |
| `--utilities-only` | Generate only utilities, skip CSS variables | - |
| `-s, --silent` | Suppress logs and prompts | - |
| `-w, --watch` | Watch for changes and regenerate automatically | - |
</Table>

Without a `src` folder, the output paths start with `styles/` instead.

### Examples

```bash frame="none"
# Zero-config - finds your resolver, uses defaults
npx sugarcube generate

# Specify resolver explicitly
npx sugarcube generate --resolver ./tokens.resolver.json

# Custom output paths
npx sugarcube generate --variables dist/tokens.css --utilities dist/utilities.css

# Override fluid viewport range
npx sugarcube generate --fluid-min 375 --fluid-max 1440

# Use polyfill for wide gamut colors
npx sugarcube generate --color-fallback polyfill

# Prefix every variable, such as --ds-color-accent
npx sugarcube generate --prefix ds

# Generate per-brand CSS files (each at :root)
npx sugarcube generate --input brand=ocean --variables dist/ocean.css --variables-only
npx sugarcube generate --input brand=forest --variables dist/forest.css --variables-only
npx sugarcube generate --utilities-only

# Generate with a custom selector
npx sugarcube generate --input theme=dark --selector "[data-theme='dark']" --variables dist/dark.css

# Override config file values temporarily
npx sugarcube generate --fluid-max 1600

# Watch mode - regenerate on token, markup or config changes
npx sugarcube generate --watch
```

### When your tokens have mistakes

`generate` prints every problem, writes no CSS, and exits with code 1. Each problem shows where it is (file, line and column), its kind, what's wrong, and the line from your file, with the fix beside it when there's a clear one. A problem in your config names only the config file:

```text frame="none"
src/design-tokens/color.json:58:17  error[missing-reference]
  `color.bleu.500` does not exist
  58 |       "$value": "{color.bleu.500}"
     |                 ^^^^^^^^^^^^^^^^^^ did you mean `color.blue.500`?

src/design-tokens/color.json:63:9  error[invalid-value]
  a color needs three components
  63 |         "components": [
     |         ^^^^^^^^^^^^

2 errors. No CSS was written.
```

Most terminals and editors turn `file:line:column` into a link. Warnings are printed too, but don't stop the build.

### Watch Mode

The `--watch` flag regenerates while you work:

- It watches exactly the token files your resolver uses, and your markup files (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.astro`, `.html` and so on) for utility class changes.
- It reloads when your config file changes.
- It keeps running when a file has a mistake, even at the start: it prints the problems, writes no CSS, and writes again once you fix them.

```text frame="none"
[sugarcube] Generated in 11ms
[sugarcube] Watching 4 token files + markup files...
[sugarcube] space.json changed, wrote src/styles/variables.gen.css (9ms)
```

Press `Ctrl+C` to stop watching.

### Flag Behavior

**Config File Priority:**
1. If a config file exists, it's loaded first
2. CLI flags override config values for that run only
3. Config file is never modified by flags

**Without Config File:**
- Finds a `*.resolver.json` file anywhere in your project, skipping `node_modules`, build folders and hidden folders such as `.storybook`
- All flags use default values unless specified
- When several resolvers could be found, set `resolver` in your config, or pass `--resolver` for one run

**Example - Testing Different Values:**
```bash frame="none"
# Your config has fluid.max = 1200
# Test with a larger viewport without changing config:
npx sugarcube generate --fluid-max 1600
# Config file still has 1200 - only this run used 1600
```

### Requirements

**One of:**
- A sugarcube configuration file, OR
- A `*.resolver.json` file in your project (found for you), OR
- The `--resolver` flag with a valid resolver file path

If none are found, the command reports that no design tokens were found and suggests running `npx @sugarcube-sh/cli init` to set up your project.

### Output

The command writes CSS files at your configured paths:

- CSS variables file (default: `src/styles/variables.gen.css`)
- Utility classes file (default: `src/styles/utilities.gen.css`)

## `validate`

Check your token files for errors.

### Usage

```bash frame="none"
npx sugarcube validate [paths...]
```

### Description

The `validate` command reads your tokens as `generate` does, and reports every problem without writing any CSS. Each problem is printed as `generate` prints it, with its file, line and column. It exits with code 1 when there's an error, so it can fail a CI check.

With no paths, it checks exactly what `generate` builds, so problems in the CSS, such as two tokens writing the same variable, fail it too.

### Arguments

<Table>
| Argument | Description |
|----------|-------------|
| `[paths...]` | Optional token files or directories to validate (e.g., `src/design-tokens`) |
</Table>

### Examples

```bash frame="none"
# Validate what generate builds, using your config
npx sugarcube validate

# A folder, through the resolver in it
npx sugarcube validate src/design-tokens

# A single token file
npx sugarcube validate tokens/colors.json
```

### Behavior

- **With no paths**: reads your config and resolver, as `generate` does, and checks what it would build.
- **A folder with a resolver**: reads the tokens through that resolver, with the settings in your config.
- **A folder with no resolver**: reads only the files that hold tokens (a DTCG property such as `$value` or `$type`), skipping `node_modules`, build folders and hidden folders. If it finds none, it names the JSON files it passed over.
- **Several token files with no resolver**: refused, because only a resolver says how they go together and in which order. Add a [resolver](/docs/resolver):

```text frame="none"
Several token files need a resolver to be read together:
  - tokens/color.json
  - tokens/space.json
```

- **Files ending `.tokens`**, the extension the spec recommends, are read too.
- **No tokens anywhere**: reports that no design tokens were found, and exits with code 1.

## `lint`

Check that your CSS and markup only use variables your tokens declare.

### Usage

```bash frame="none"
npx sugarcube lint [paths...] [options]
```

### Description

When you write `var(--color-primary)` in your CSS, `lint` checks that the variable actually exists. It catches typos and references to tokens you've renamed or deleted.

sugarcube has three checks, each answering a different question:

<Table>
| Command | Looks at | Answers |
|---------|----------|---------|
| [`validate`](#validate) | Your token files | Pass or fail |
| `lint` | Your CSS and markup | Pass or fail |
| [`analyze`](#analyze) | What's true of your token system | A report |
</Table>

Coming from Terrazzo? There, `tz lint` checks tokens. In sugarcube that's `validate`. `lint` checks the CSS that uses them.

A variable exists if sugarcube generates it from your tokens, if a utility class sets it, or if you declare it yourself in one of the scanned files. Everything else is undeclared, and there are two kinds:

- Without fallback, like `var(--missing)`. This is an error: the browser has nothing to use, so it drops the whole declaration.
- With fallback, like `var(--missing, 1rem)`. This is a warning: the browser uses your fallback, so the page still renders. Pass `--fallback error` to treat these as errors too, or `--fallback off` to hide them.

```text frame="none"
■  References without fallback (1)
│
│  src/styles/global.css
│   3  var(--color-border)
│
▲  References with fallback (1)
│
│  src/styles/global.css
│   3  var(--space-xl, …)
│
└─  1 without fallback, 1 with fallback  6 variable references in 2 files
```

### Arguments

<Table>
| Argument | Description |
|----------|-------------|
| `[paths...]` | Directories or globs to scan, e.g. `../css`. Defaults to your project's CSS and component files, plus anything in `content`. |
</Table>

Pass a path when your stylesheets live outside the directory you run from and you'd rather not change your config. To make it the default for every run, add the same location to [`content`](/docs/configuration#telling-sugarcube-which-files-to-scan) instead.

### Options

<Table>
| Option | Description | Default |
|--------|-------------|---------|
| `--ignore <prefixes>` | Comma-separated variable-name prefixes to skip (e.g. third-party vars) | - |
| `--fallback <level>` | How to treat references that have a fallback: `error`, `warn`, or `off` | `warn` |
| `--json` | Output JSON instead of formatted text | - |
</Table>

With `--json`, the undeclared references are in `withoutFallback` and `withFallback`, each with its `name`, `file` and `line`.

### Supported files

`lint` reads CSS from `.css` files and from `<style>` blocks in `.html`, `.htm`, `.vue`, `.svelte`, `.astro` and `.php` files. It doesn't read `<style>` blocks in other templates, such as `.njk`, `.erb` or `.heex`, CSS written in JavaScript, or preprocessor files (`.scss`, `.sass`, `.less`, `.styl`). It skips build folders, dependencies, and the CSS files sugarcube generates.

This is only about finding CSS: sugarcube finds the utility classes you use in all of these templates, `.jsx` and `.tsx` included.

When it finds no stylesheets anywhere, it says so rather than reporting a pass, and shows how to point it at your CSS: add it to `content`, such as `content: ["../css/**/*.css"]`, or name it for one run, `sugarcube lint ../css`.

### Requirements

Like [`generate`](#generate), this works **zero-config** (a `sugarcube.config.ts` is optional). It needs to find your tokens, from either:

- A sugarcube configuration file, OR
- A `*.resolver.json` file in your project (found for you)

If neither is found, the command reports that no design tokens were found. It needs them to know which CSS variables your tokens actually generate — without that it can't tell an undeclared reference from a valid one.

If your tokens have mistakes, `lint` prints them as [`generate`](#when-your-tokens-have-mistakes) does, then "Nothing was linted.", and exits with code 1. With `--json`, the problems go to stderr.

### Examples

```bash frame="none"
# Lint the whole project (CSS + components)
npx sugarcube lint

# Lint specific files or globs
npx sugarcube lint "src/**/*.css" "src/**/*.vue"

# Lint a directory, including one above where you're running from
npx sugarcube lint ../css

# Also fail on references that only have a fallback
npx sugarcube lint --fallback error

# Hide references that have a fallback
npx sugarcube lint --fallback off

# Ignore third-party variable prefixes
npx sugarcube lint --ignore "--sl-,--radix-,--tw-"

# Machine-readable output for CI
npx sugarcube lint --json
```

### Exit codes

`lint` exits `0` when there are no undeclared references, and `1` when there's at least one. Fallback-only references pass unless you run with `--fallback error`, which makes them fail too. That makes `lint` a good CI check: run `npx sugarcube lint` to catch missing token references before they ship.

It also exits `1` when your tokens have mistakes, and when it found no stylesheets to read, since those are a command that couldn't run rather than a project with nothing wrong. Reading *some* of your CSS still exits `0`: you get the warning, not a failure.

## `analyze`

Find unused tokens, and what a change to a token affects.

### Usage

```bash frame="none"
npx sugarcube analyze <subcommand> [options]
```

### Description

Where `lint` and `validate` answer pass or fail, `analyze` answers questions. It follows the references between your tokens in every permutation it writes, private tokens and `$ref` pointers included, and finds where your CSS and markup use them. What it finds isn't an error, so a report exits `0`.

If your tokens have mistakes, it prints them as [`generate`](#when-your-tokens-have-mistakes) does, then "Nothing was analysed.", and exits with code 1.

It has two subcommands: `unused` and `impact`.

### `analyze unused`

List tokens nothing in your CSS or markup uses, directly or through other tokens.

```bash frame="none"
npx sugarcube analyze unused [options]
```

<Table>
| Option | Description | Default |
|--------|-------------|---------|
| `--all` | Print every unused token path, one per line, with no formatting | - |
| `--json` | Output JSON instead of formatted text | - |
</Table>

Results are grouped so a family with many unused steps reads as one row, and `all` means every token in a group of several is unused. Part of the output for this site's own tokens:

```bash frame="none"
npx sugarcube analyze unused
```

```text frame="none"
Group                  Unused   Tokens
─────────────────────────────────────────────────
color.accent.border         1   loud
color.accent.on             1   quiet
color.alpha.black           5   00 12 15 25 80
color.alpha.white           2   all
color.amber                 3   300 400 950
color.blue                  3   300 400 950

264 of 489 tokens unused. Read 115 stylesheets and 232 markup files.
```

Use `--all` when you want to pipe the result somewhere:

```bash frame="none"
# Every unused token path, one per line
npx sugarcube analyze unused --all

# Count them
npx sugarcube analyze unused --all | wc -l
```

With `--json`, you get the `unused` paths, the `total` number of tokens, and how many files were `scanned`, as `stylesheets` and `markup`.

<SiteAside type="caution">
    Unused doesn't necessarily mean deletable. A token may be referenced by markup sugarcube can't see, consumed by another package, or part of an API you publish deliberately. Treat the list as a starting point for a decision, not a blind to-do list.
</SiteAside>

### `analyze impact`

Show what changing a token affects.

```bash frame="none"
npx sugarcube analyze impact <token> [options]
```

Before renaming or changing a token, this answers "what breaks?": the tokens that reference it, directly or through a chain, and the CSS and markup that use any of them.

<Table>
| Argument | Description |
|----------|-------------|
| `<token>` | Token path, e.g. `color.pink.600` |
</Table>

<Table>
| Option | Description | Default |
|--------|-------------|---------|
| `--json` | Output JSON instead of formatted text | - |
</Table>

```bash frame="none"
npx sugarcube analyze impact color.neutral.900
```

The chains are drawn as a tree. A child references its parent, so depth is the number of hops. For this site's own tokens:

```text frame="none"
Token                               Uses   Where
──────────────────────────────────────────────────────────────────────────────
color.neutral.900                      0
├─ color.neutral.on.loud               7   css/badge.css  react/badge.css  +5 more
│  └─ color.on.loud                    8   css/badge.css  react/badge.css  +6 more
├─ color.neutral.fill.quiet            0
│  └─ color.fill.quiet                 0
├─ color.neutral.surface.lowered       0
│  └─ color.surface.lowered            6   tabs.css  site-card.css  +3 more
├─ color.neutral.surface.raised        0
│  └─ color.surface.raised            12   css/card.css  react/card.css  +10 more
└─ color.neutral.text.normal           0
   └─ color.text.normal               28   accordion.css  dropdown-menu.css  +9 more
      ├─ form-control.label.color      3   css/label.css  react/label.css  global.css
      └─ form-control.value-color      1   global.css

65 uses in 32 files.
```

`Where` names the stylesheets and markup files that use each token, with a folder when two files share a name, as `css/badge.css` and `react/badge.css` do.

When a token's value differs between contexts, the first line shows each value:

```text frame="none"
color.accent.on.loud   {color.pink.50}   {color.white}
```

`impact` takes one token. For a group, it says so: `` `color.blue` is a group; impact takes one token. `` For a token that doesn't exist, it says `No token "color.nope" in this system.` Both exit with code 1.

With `--json`, you get the `token`, its `definitions` (one per place it's written, each with its `value`, `type`, `file` and `permutations`), its `dependents`, and its `uses`, each with the `file` and `line`, and the variable or class used.

### Examples

```bash frame="none"
# What's unused?
npx sugarcube analyze unused

# What would this rename break?
npx sugarcube analyze impact color.brand.fill

# Machine-readable
npx sugarcube analyze unused --json
npx sugarcube analyze impact space.md --json
```

### Where analyze looks

`analyze` scans the CSS below your working directory plus everything in [`content`](/docs/configuration#telling-sugarcube-which-files-to-scan), and reads markup files for the utility classes they use.

When the scan reaches no stylesheets at all, `analyze` says so before its report, because the report can't be trusted.

It warns about a partial scan too (i.e. when it knows, based on your configuration, that you have stylesheets somewhere but they are not being read):

```text frame="none"
Didn't read 255 stylesheets in ../css

Tokens used only there appear unused. Add the folder to content.
```

The cause is almost always a missing `content` entry. Add the folder to `content` (i.e. tell sugarcube where to find your stylesheets) and the warning goes away.

## `components`

Install copy-to-use components for your framework.

### Usage

```bash frame="none"
npx sugarcube components [components...] [options]
```

### Description

The `components` command allows you to browse and install pre-built components from the sugarcube component registry. Components are installed as copy-to-use files in your project.

### Arguments

<Table>
| Argument | Description |
|----------|-------------|
| `[components...]` | Optional component names to install (e.g., `button card`) |
</Table>

### Options

<Table>
| Option | Description |
|--------|-------------|
| `-f, --framework <type>` | Framework to use (`react`, `css-only`) |
| `-o, --output <dir>` | Components output directory (auto-detected based on `src/`, or from config) |
| `-s, --silent` | Suppress logs and prompts |
| `--force` | Overwrite existing files without confirmation |
</Table>

### Examples

```bash frame="none"
# Interactive mode - browse and select components
npx sugarcube components

# Install specific components
npx sugarcube components button card --framework react

# Install CSS-only components
npx sugarcube components button --framework css-only

# Specify custom output directory
npx sugarcube components button --output src/ui

# Overwrite existing files
npx sugarcube components button --force
```

### Behavior

- **Interactive mode**: If no components or framework are specified, you'll be prompted to select a framework and browse available components
- **Non-interactive mode**: Requires `--framework` flag when specifying components
- **Dependencies**: Automatically installs required npm dependencies for React components
- **Overwrite warnings**: Shows warnings before overwriting existing files (unless you pass `--force` or `--silent`)
- **Works without a config file**: Defaults to `src/components/ui` or `components/ui` based on whether your project has a `src/` directory. Use `--output` to override.
- **Does not modify config files** - flag values are temporary for the command run

### Supported Frameworks

- `react` - React components with TypeScript
- `css-only` - Pure CSS components

## `cube`

Add CUBE CSS architecture to your project.

### Usage

```bash frame="none"
npx sugarcube cube [options]
```

### Description

The `cube` command installs the CUBE CSS methodology files into your project. CUBE CSS (Composition, Utility, Block, Exception) provides a structured approach to writing CSS.

### Options

<Table>
| Option | Description |
|--------|-------------|
| `-s, --silent` | Suppress logs and prompts |
| `--force` | Skip overwrite confirmation |
| `-o, --output <dir>` | CUBE CSS output directory (auto-detected based on `src/`, or from config) |
</Table>

### Examples

```bash frame="none"
# Add CUBE CSS files
npx sugarcube cube

# Specify custom output directory
npx sugarcube cube -o src/styles/cube

# Skip overwrite confirmation
npx sugarcube cube --force

# Silent mode
npx sugarcube cube --silent
```

### Output

The command creates CUBE CSS directory structure in your configured styles directory:

```
<styles-dir>/
├── blocks/
├── compositions/
├── global/
└── utilities/
```

Each directory includes starter files. These are starting points that you can modify, add to, or remove as needed.

### Behavior

- Creates the output directory if it doesn't exist
- Shows warnings before overwriting existing files (unless you pass `--force` or `--silent`)
- **Works without a config file**: Defaults to `src/styles` or `styles` based on whether your project has a `src/` directory. Use `-o` to override.
- **Does not modify config files** - flag values are temporary for the command run

## Command Workflow

A typical sugarcube workflow:

1. **Initialize** your project:
   ```bash frame="none"
   npx @sugarcube-sh/cli init
   ```

2. **Generate CSS** (if not using Vite plugin):
   ```bash frame="none"
   npx sugarcube generate

   # Or use watch mode during development
   npx sugarcube generate --watch
   ```

3. **Add components** as needed:
   ```bash frame="none"
   npx sugarcube components
   ```

4. **Add CUBE CSS** (optional):
   ```bash frame="none"
   npx sugarcube cube
   ```

5. **Validate tokens** during development:
   ```bash frame="none"
   npx sugarcube validate
   ```

6. **Lint your styles** for undeclared token references (great in CI):
   ```bash frame="none"
   npx sugarcube lint
   ```

7. **Analyze your token system** when you want to understand it rather than check it:
   ```bash frame="none"
   npx sugarcube analyze unused
   npx sugarcube analyze impact color.brand.fill
   ```

## Getting Help

For more information about a specific command:

```bash frame="none"
npx @sugarcube-sh/cli <command> --help
```
